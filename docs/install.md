# Installing jj-ci

[jj-ci](../README.md) is a nushell module that is also a runnable script. There
is nothing to compile and nothing to add to `PATH` unless you want to.

Developed and tested against **jj 0.45.1** and **nushell 0.115.1**. It relies on
`jj run --ignore-changes` and `--passthrough`, which landed in jj 0.44, so 0.44
is the practical floor; the nushell floor has not been measured, but the code
uses raw strings, `def --wrapped` and `get -o`, none of which are ancient.

## Two ways in, one file

The root `mod.nu` is both the module and the script. `bin/jj-ci` is a symlink to
it, so both reach the same code:

```nushell
use ~/Scripts/jj-ci    # jj-ci ci, jj-ci push, … with native help and completion
```

```bash
~/Scripts/jj-ci/bin/jj-ci ci    # the same commands as a script
```

Add the `use` line to your nushell config and `jj-ci <TAB>` completes on its
own, with real signatures — nushell knows the module. The jj aliases below go
through jj rather than through nushell, so they still want the generated
`extern` file.

The command prefix is the **directory's basename**: clone this somewhere called
`jj-ci` or your commands will be named after wherever you put it. `use <dir> as
jj-ci` does not help — `as` renames an export, not a module.

One consequence of the `use` line worth knowing: from then on a syntax error in
jj-ci is a syntax error in your shell startup, not just a broken jj-ci. The
`parse` and `load` checks in this repository's own `.jj-ci.toml` exist partly
for that.

## The git hooks

In a git repository `jj-ci install` writes `pre-push` and `commit-msg` instead,
into `.git/hooks` or wherever `core.hooksPath` points:

```bash
~/Scripts/jj-ci/bin/jj-ci install
```

Each hook names the nushell interpreter and jj-ci itself by absolute path,
because a hook inherits whatever environment spawned it and a GUI git client
usually has none of your `PATH`.

**Re-run the command whenever either path moves.** Under Nix that is every
update of nushell, since its store path changes; it is also what happens if you
move jj-ci itself. Re-running rewrites both paths in place and reports
`refreshed` rather than `wrote`. A hook jj-ci wrote is always overwritten; one
it did not write is never touched — the lines to add are printed instead, so a
repository already running husky or lefthook stays yours to wire up.

A hook whose paths have moved is not silently dead. It falls back to whatever
`nu` is on `PATH`, so in a terminal the gate keeps working, and when there is
no `nu` either it exits nonzero saying to run `jj-ci install` again rather than
leaving you a bare `No such file or directory`. `jj-ci doctor` names the moved
path, so it is worth a glance after a rebuild.

What the two hooks check, and what else differs under git, is
[git.md](./git.md).

## The jj aliases

Two jj aliases gate `jj push`. jj refuses to load command aliases from
`--config`, `--config-file` or `-R` — they must be in a real config file — and
the user-level one is what makes them available in every repository:

```bash
~/Scripts/jj-ci/bin/jj-ci install
```

That prints the block for `~/.config/jj/config.toml` and, below it, the
home-manager equivalent. Nothing is written: on a machine where that file is
generated by a dotfile manager, writing to it either fails or is reverted on
the next rebuild. Use `--write` only if you maintain the file by hand.

Add `--on-path` if `bin/jj-ci` is on your `PATH` and you would rather the alias
said `jj-ci` than an absolute path.

## Nushell completions

This is for the **`jj ci` / `jj push` aliases only** — `jj-ci …` as a module
needs nothing, since nushell has the real signatures.

Nushell sees `jj` as one external binary, so `jj ci --<TAB>` completes nothing
and `jj ci --help` prints *jj's* help. An `extern` declaration for the two-word
command fixes both. The command returns the module rather than printing it, so
it pipes:

```nushell
jj-ci completions nushell | save -f ~/.config/nushell/completions/jj-ci.nu
# then, in your config: source ~/.config/nushell/completions/jj-ci.nu
```

`jj util completion nushell` overwrites one file and cannot know about aliases,
so this is a second file beside it. `jj-ci install` prints a home-manager
activation snippet that regenerates it on every switch, the way jj's own
completions are generated.

Only nushell is shipped. The flags are documented in
[commands.md](./commands.md); another shell is a short script away.
